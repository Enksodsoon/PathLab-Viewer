# Receipt Schema Registry

This registry freezes the machine-readable evidence types required by the Golden Institution Journey. A receipt proves one committed domain or governance disposition; a result proves one evaluated invariant or campaign. Neither changes the authority of the source aggregate unless its row explicitly says so, and neither implies a Delivery State Ledger transition unless its row explicitly names that transition.

## Schema and envelope rules

Every registered type uses JSON Schema 2020-12, the exact schema ID and semantic version below, and canonical JSON bytes. Signature authority is selected by the discriminated scope below; an Institution-authorized signature Key Version is mandatory for Institution scope but cannot be fabricated for a repository, release, or installation that has not created an Institution yet. The repository artifact for a schema ID is:

```text
schemas/evidence/<bounded-context>/<type>/1.0.0.schema.json
```

Every receipt, result, observation, or evidence manifest contains this common envelope in addition to its row-specific subject fields:

- `schema_id` and `schema_version` exactly matching this registry;
- globally unique evidence identity, `scope_kind` with exactly one of `REPOSITORY`, `RELEASE`, `INSTALLATION`, or `INSTITUTION`, and an immutable `scope_subject_id` appropriate to that kind;
- `institution_id`: a non-null exact Institution identifier when `scope_kind=INSTITUTION`; JSON `null` is permitted only for the other three scope kinds. An optional Institution reference outside Institution scope is contextual metadata and never changes scope or authority;
- source authority type, source subject type/id/version, source event or run id, and—when Institution-scoped—the authoritative bounded context and source aggregate type/id/version/event;
- command or evaluation identity, idempotency key, trusted event time, disposition, and terminal/non-terminal status;
- issuer type/id, accountable actor or controller, signing-authority type and key identity/version; Institution-scoped evidence additionally requires the actor or Service Principal, applicable Role Binding and Purpose Identity references, policy and Institution Key Versions, and accountable approver references without authenticator secrets;
- the exact repository/source subject and every release, artifact, configuration, deployment profile, host, backup target, client, standards corpus, and fixture identity required by the row and current scope/state; outputs that do not exist yet are explicitly null/not-applicable and cannot be inferred or backfilled into the signed receipt;
- subject hashes, counts and byte totals required by the row, plus content-hash references to supporting artifacts rather than mutable paths;
- predecessor evidence-chain reference or the schema-defined genesis marker, plus signature metadata; Institution-scoped evidence uses the Audit Integrity Chain;
- retention trigger, deletion classification, privacy classification, expiry or review time, and unresolved obligations; and
- when used in the Golden Institution Journey, `journey_run_id`, step id, immutable command hash, predecessor journey receipt hash, fault ids and cleanup obligation ids.

`scope_subject_id` is never a mutable label: repository scope binds the repository identity plus exact task/change/commit subject, release scope binds an immutable release/candidate identity and requires its artifact root as soon as assembly exists, installation scope binds the signed installation identity plus target identity, and Institution scope binds the Institution plus the row's domain or governance subject. The schema enforces these scope-specific signing authorities:

- `REPOSITORY`: a repository governance or protected-check authority whose verification key is pinned by protected repository configuration;
- `RELEASE`: a protected build runner or release controller whose attestation key is pinned by repository release policy and the immutable release provenance;
- `INSTALLATION`: a named installation Operator, deployment controller, or installation-scoped `svc-platform` identity whose key and authority are declared by the signed installation manifest; and
- `INSTITUTION`: a currently authorized human or Service Principal whose Institution Key Version, Membership/Role Binding where human, policy, and owning-context authority all verify.

Pre-Institution evidence must use `REPOSITORY`, `RELEASE`, or `INSTALLATION`, set `institution_id` and all Institution Principal, Role Binding, and Purpose Identity fields to JSON `null`, and verify its separate issuer against the corresponding pinned trust root above. It cannot create product-domain authority, impersonate an Institution Principal, or satisfy an Institution-scoped gate. From Trust and Governance onward, every domain/governance row is `INSTITUTION` scoped unless its row explicitly states otherwise; choosing a pre-Institution scope for such a row is invalid.

Secrets, PHI, private slide pixels, learner answers, participant-level telemetry, raw authenticator material and private infrastructure addresses are prohibited from evidence envelopes. A sanitized verification copy may redact declared display fields but must preserve source hashes, signature verification and disposition.

`SUCCESS`, `PARTIAL`, `NEGATIVE`, and `NOT_EVALUABLE` are gate-result values, not lifecycle states. Domain receipts use only the dispositions frozen in their row. Unless a row says otherwise, its Delivery State Ledger effect is **evidence-only**: it may be cited by a later lifecycle receipt but cannot itself move `PLANNED`, `IMPLEMENTED`, `CHECKED_LOCAL`, `CHECKED_PROTECTED`, `MERGED`, `DEPLOYED`, `PILOT_VALIDATED`, `PRODUCTION_QUALIFIED`, `ACTIVATED`, or `ACTIVATION_SUSPENDED`.

These records are verified from their owning source event, aggregate version and canonical hash. They must be referenced by the appropriate registered receipt or result where the journey expects evidence, but they must not be wrapped in a generic “success receipt” that obscures their authority or lifecycle.

## Evaluable-journey gate

Logs, console output, screenshots, UI banners, HTTP status alone, external-provider acknowledgements, mutable database queries, manually edited reports and unsigned test summaries cannot substitute for a registered receipt or result. A receipt cannot be reconstructed after the fact from logs when its source event and signature were not committed under the registered schema.

Before `JourneyAdmissionReceipt(READY)` is possible:

1. every schema artifact named by the immutable Golden Journey Manifest exists at its repository path, declares the exact `$id` and version above, rejects unknown required semantics, and has offline-valid positive and adversarial fixtures;
2. every emitting context validates before commit and every consumer validates before accepting evidence;
3. the release's schema-registry digest, validator digest and supported versions are bound into the Offline Release Kit and Journey Manifest;
4. signature, privacy, retention, deletion and predecessor-chain checks pass for every prerequisite receipt; and
5. the complete manifest-to-schema coverage check reports no unregistered receipt, result, observation, report or receipt alias.
6. the manifest's complete final-candidate fingerprint hash equals the deployed `P7-T12` fingerprint, and the live current-deployment projection identifies the exact same `DeploymentSelectionReceipt(SELECTED)` head, release/artifact/configuration/migration/upstream-route digests and route; a changed or `REVERTED` head is an admission failure.

Any missing schema, source-event binding, owner, validator, signature, subject field, disposition, lifecycle effect, fixture, privacy proof, or coverage entry makes the journey `NOT_EVALUABLE`. Schema evolution creates a new immutable semantic version and artifact; the Journey Manifest pins exactly one accepted version for each type, and no alias or best-effort parser may silently reinterpret evidence.
