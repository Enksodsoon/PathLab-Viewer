# Clinical and Imaging Interoperability

This contract admits only synthetic material or source packages that an Institution has already attested as deidentified under the permanent `DEIDENTIFIED SHADOW — NOT FOR CLINICAL USE` boundary. Encrypted quarantine treats every received byte as potentially identifying until independent validation completes because an attestation or detector can fail. No authorized v1 workflow knowingly sends raw PHI to PathLab, and PathLab is not a raw-PHI deidentification service: any residual identifier, unsafe metadata, OCR/pixel finding, or invalid confidentiality action causes rejection and bounded destruction rather than repair or admission. This contract creates no diagnostic, patient-care, writeback, or general standards-conversion claim.

## FHIR wire contract

- Freeze FHIR R4 4.0.1. The upstream `GET /metadata` response must declare `CapabilityStatement.fhirVersion = 4.0.1`.
- Requests and responses use JSON with `Accept: application/fhir+json; fhirVersion=4.0`; R4B, R5, missing, conflicting, or ambiguous version evidence is rejected without conversion.
- The Integration Gateway may perform only bounded `GET /metadata`, `read`, and `search` calls required by the admitted profile.
- POST, PUT, PATCH, DELETE, transaction/batch, history, `$everything`, Bulk Export, subscriptions, and every Clinical Writeback path are unsupported and unadvertised.
- Clinical Shadow stores a local read-only projection. It is not a general FHIR server and cannot influence a patient-care source.

### Executable FHIR profile package

- The executable contract is the immutable package `pathlab.fhir.shadow.r4#1.0.0`, with canonical base `https://fhir.pathlab.invalid/r4` and an exact dependency on `hl7.fhir.r4.core#4.0.1`. The release manifest records the package and artifact SHA-256 digests; a missing artifact, different dependency, digest mismatch, or unresolved canonical blocks build and admission.
- The package contains `package.json`, `.index.json`, `ImplementationGuide/pathlab-shadow-r4`; differential and snapshot `StructureDefinition` resources named `pathlab-shadow-case-bundle`, `pathlab-shadow-patient`, `pathlab-shadow-specimen`, `pathlab-shadow-imaging-study`, `pathlab-shadow-diagnostic-report`, `pathlab-shadow-observation`, and `pathlab-shadow-endpoint`; `CapabilityStatement/pathlab-shadow-client` with `rest.mode=client`; the complete required core-binding closure; PathLab terminology `ValueSet` resources and `CodeSystem/pathlab-shadow-rejection`; positive and negative examples; and a machine-readable rejection map.
- A signed search-template manifest fixes the only permitted resource types, parameters, combinations, sort behavior, page size, page count, total-result limit, timeout, and response byte limit for each External Registration. A query that cannot be produced from an exact registered template, an unbounded continuation, and a server-supplied next link outside the registered origin are rejected before retrieval.
- Every local FHIR validation or admission failure is represented by a FHIR R4 `OperationOutcome` whose `issue.severity` is `error` or `fatal`, whose `issue.code` is a frozen core IssueType, whose `details.coding` is a stable PathLab rejection code, and whose `expression` identifies the offending path when safe. Outcomes are sanitized and contain no raw clinical value or untrusted narrative; malformed/version errors use `400`, replay or identity conflicts `409`, size-limit failures `413`, profile, terminology, reference, or deidentification failures `422`, and inconsistent or unavailable upstream responses `502`.
- An `OperationOutcome` alone never represents a successful read or admission. An upstream error outcome is stored as bounded failure evidence and cannot be accepted as a requested resource, while an invalid or unrecognized outcome is itself rejected.

### Shadow Case Bundle

- One `Bundle` with `type=collection` contains exactly one `Patient`, one `Specimen`, one `ImagingStudy`, one `DiagnosticReport`, one PathLab-generated `Endpoint`, and zero or more `Observation` resources; no other resource is admitted.
- `Patient` contains only a PathLab pseudonymous identifier. Names, telecom, address, photo, contact, birth date, and other demographics are prohibited.
- The Bundle and every entry declare the corresponding package canonical in `meta.profile` with version `|1.0.0`; every reference resolves within the accepted bundle, and duplicate, dangling, contained, or arbitrary external references are rejected.
- `ImagingStudy` series and instance UIDs must equal the already-deidentified DICOM collection. The local `Endpoint` resolves to a same-origin read-only DICOMweb URL instead of importing an upstream URL.
- Narrative HTML, attachments, Binary, DocumentReference, arbitrary notes/free text, unknown extensions or modifier extensions, and source identifiers such as accession or MRN are prohibited.
- Source, ingest, inspection, and deidentification provenance stays in the signed PathLab-native manifest rather than expanding the FHIR identity surface.

### Terminology admission

- FHIR R4 code systems required by the base specification to express profiled protocol structure and administrative state are frozen from the executable `hl7.fhir.r4.core#4.0.1` dependency closure. These include required Bundle, resource-status, OperationOutcome severity, and IssueType bindings; they are protocol vocabulary, not permission to introduce clinical semantics from those systems or from arbitrary FHIR terminology.
- The base binding on `Endpoint.connectionType` is only Example. PathLab's executable profile makes its one admitted same-origin DICOMweb connection code mandatory as a stricter local constraint and freezes that code in the package; the evidence must label this as a PathLab profile rule rather than a required FHIR core binding.
- Clinical semantic admission contains audited DICOM DCM concepts, UCUM units, and only the exact LOINC release and content that the Institution is authorized to use. Every permitted system, version, code, value set or expansion, display policy, and rights record is identified in the Exchange Profile and release evidence.
- DICOM Microscopy Bulk Simple Annotations use the sole v1 property category `(111050, DCM, "Quality Assessment")` and a property type of either `(131501, DCM, "Usable tissue")` or `(131502, DCM, "Unusable tissue")`. This frozen DCM-only specialization of the extensible ANN baseline context groups is exercised against independent validators; annotations with any other semantic pair remain native PathLab annotations and cannot be labeled or exported as the v1 DICOM ANN profile.
- Validation uses frozen offline artifacts. It never depends on a hosted terminology service, mutable expansion endpoint, or a code display supplied by an untrusted exchange.
- SNOMED CT, an unknown code system or version, a code outside the admitted frozen set, and an unfrozen expansion are rejected. An Institution may add one only through a reviewed rights and validation package followed by complete requalification.

## DICOM and DICOMweb wire contract

- Freeze the DICOM 2026c edition and the applicable requirements in PS3.2, PS3.3, PS3.4, PS3.5, PS3.6, PS3.10, PS3.15, PS3.16, and PS3.18. Later corrections or editions require a reviewed compatibility decision rather than silent adoption.
- Admit only VL Whole Slide Microscopy Image Storage (`1.2.840.10008.5.1.4.1.1.77.1.6`) and Microscopy Bulk Simple Annotations Storage (`1.2.840.10008.5.1.4.1.1.91.1`). Any other SOP Class is rejected before persistence.
- Expose a read-only DICOMweb origin that implements every mandatory QIDO-RS Search and WADO-RS Retrieve resource listed in PS3.18 Table 10.3-2. The conformance corpus must cover searches across all studies, study series and instances, all series, series instances, and all instances, plus study, series, and instance retrieval, metadata and rendered retrieval, frame and rendered-frame retrieval, and bulk-data retrieval.
- Implement the PS3.18 Retrieve Capabilities transaction: `OPTIONS` to the DICOMweb service Base URI returns a `200` Capabilities Description using the frozen `application/json` representation and declares only the qualified read operations, media types, and limits. Wrong methods, undocumented capabilities, a response inconsistent with the Conformance Statement, and capability discovery at an unregistered origin fail qualification.
- Publish an exact DICOM Conformance Statement identifying the edition, SOP Classes, resources, media types, transfer syntaxes, query keys, limits, status codes, and unsupported operations. Passing only a smaller route subset permits the label `DICOMweb-compatible read-only subset`, never `DICOMweb conformant`.
- Do not expose STOW-RS, DIMSE, UPS, worklist, storage commitment, query/retrieve write paths, or Clinical Writeback. `POST`, `PUT`, `PATCH`, and `DELETE` return `405`; an upstream clinical system is never modified.
- Keep the same-origin DICOMweb Endpoint and all DICOM Study, Series, and SOP Instance UIDs equal to the accepted Shadow Case Bundle. UID rewriting after acceptance is prohibited.

### Bounded microscopy object profile

- A VL Whole Slide Microscopy object represents exactly one admitted specimen, one optical path, and one focal plane. Multiple specimens, channels, optical paths, focal planes, or concatenations are rejected rather than flattened or guessed.
- Pixel data is calibrated 8-bit color and uses `DimensionOrganizationType=TILED_FULL`. Total-pixel-matrix origin, physical pixel spacing, tile dimensions, frame positions, and the specimen-to-image relationship must be complete and internally consistent so every frame maps deterministically into the volume.
- Accept only Explicit VR Little Endian (`1.2.840.10008.1.2.1`), JPEG Baseline Process 1 (`1.2.840.10008.1.2.4.50`), JPEG 2000 Image Compression Lossless Only (`1.2.840.10008.1.2.4.90`), and JPEG 2000 Image Compression (`1.2.840.10008.1.2.4.91`). The declared Photometric Interpretation must be valid for the chosen transfer syntax and decode to the bounded color model; transcoding is not an ingest repair mechanism.
- A Microscopy Bulk Simple Annotations object references exactly one admitted WSI SOP Instance, uses two-dimensional image coordinates with `PixelOriginInterpretation=VOLUME`, and preserves that immutable reference through export.
- Annotation groups may contain only `POINT`, `POLYLINE`, `POLYGON`, `ELLIPSE`, or `RECTANGLE` geometry. Coordinates must be finite, in bounds, structurally valid for the declared graphic type, and non-self-intersecting where the type requires a closed region.
- Every annotation group carries the frozen DCM property category and type, generation type, minimized authoring identity or device provenance, and deterministic algorithm identification when generation is automatic or semiautomatic. The Type-1 ANN Content Date and Content Time carry only the nonidentifying replacements defined by the deidentification policy; true derivative generation and review times remain in the signed PathLab-native manifest. Unknown semantics or coordinate systems, incomplete algorithms, unsupported geometry, or ambiguous provenance are rejected.

## DICOM deidentification admission gate

- Admission starts only from a synthetic or Institution-attested already-deidentified package. The quarantine validator checks the candidate against the DICOM 2026c Basic Application Level Confidentiality Profile with the Clean Pixel Data, Clean Recognizable Visual Features, Clean Graphics, Clean Structured Content, and Clean Descriptors options. The applicable PS3.15 table is copied into a versioned, machine-readable tag/action policy with a source citation and policy digest; ad hoc tag lists are not authoritative, and validation never repairs a package containing residual PHI into admissibility.
- Do not use any Retain Patient Characteristics, Retain Device Identity, Retain Institution Identity, Retain UIDs, Retain Safe Private, or other identity-preserving option. Reject every private element, private creator, unknown element, overlay, embedded object, or unsupported encoding rather than guessing whether it is safe.
- The admitted representation contains no original source date or time in v1 and never shifts one or retains longitudinal relationships. The machine-readable PS3.15 action policy requires `X` removal, permits `Z` zero length only where the IOD permits it, and requires `D` or Type-1 `Z/D` to hold a deterministic nonidentifying dummy valid for the attribute's VR and cardinality; a candidate with the original value, an invalid omission, or an invalid zero-length value is rejected.
- Generated ANN objects set the required Content Date `(0008,0023)` to `19000101`, Content Time `(0008,0033)` to `000000.000000`, and Longitudinal Temporal Information Modified `(0028,0303)` to `REMOVED`. FHIR profiles prohibit source temporal elements, and real ingest, derivative-generation, inspection, and approval times exist only in the signed PathLab-native manifest; these operational times are not copied into an exchange object.
- A later purpose-specific temporal profile must name its PS3.15 option, privacy analysis, intended utility, and independent qualification before it can admit shifted time.
- Before admission, verify that coded values and descriptors already satisfy the reviewed policy; a disallowed or identifying value rejects the candidate. Only after the attested-deidentified candidate passes every residual-PHI rejection check may PathLab generate a purpose-specific exchange derivative with keyed UID replacements derived from the already-deidentified UIDs while preserving internal Study, Series, Instance, and annotation references. This privacy-hardening derivative cannot repair a failing candidate into admissibility, never exposes the input UIDs, and prohibits cross-purpose linkability.
- Inspect all metadata and structured content with the tag/action validator. Run OCR and prohibited-pattern scanning over label, overview, thumbnail, and other associated images plus a deterministic coverage set of volume frames; flag visible faces, labels, burned-in graphics, handwriting, barcodes, and identifiers.
- Keep inbound attested-deidentified candidates in an encrypted quarantine with no user, API, backup, search, or derivative visibility. Quarantine is a rejection boundary, not permission to process knowingly identifiable input; any unexpectedly identifying byte is incident evidence and is destroyed within the 24-hour ceiling. Two distinct people must approve release: an Institution-designated privacy or data steward reviews the metadata, policy, purpose, and prohibited findings, and a WSI-capable visual reviewer examines associated images and sampled volume coverage.
- An admission receipt records the source digest, policy version and digest, tool versions, UID-map scope, automated findings, both reviewers and review times, accepted object digests, and Purpose Grant. Either rejection blocks admission; any later identity finding revokes the receipt, blocks delivery, and starts the incident and deletion workflow.
- Each retrieval or refresh produces a new immutable quarantined snapshot with a new source digest and repeats every automated and human gate. Clinical Shadow performs no scheduled synchronization, silent replacement, inherited approval, or automatic promotion.

## OME-Zarr exchange contract

- PathLab generates an immutable exchange derivative conforming to OME-Zarr specification revision **0.5.2** on Zarr format v3 from the same normalized source used for other derivatives; the on-wire OME metadata version remains the required string `"0.5"`. It independently reads and validates the completed hierarchy before publication, but v1 never admits an arbitrary OME-Zarr hierarchy as a Source Asset or authoritative input.
- One representation contains exactly one calibrated `uint8` two-dimensional RGB multiscale image with array order `c,y,x`, fixed red, green, and blue channels, micrometer spatial units, matching array `dimension_names`, and an explicit scale transform for every resolution level ordered from highest to lowest resolution.
- The root image group's Zarr v3 `zarr.json` has `node_type="group"` and `zarr_format=3`; its `attributes` object has one `ome` member containing `version="0.5"`, the single `multiscales` declaration, and standard transitional `omero` display metadata for the fixed RGB channels. Each resolution array named by `multiscales.datasets[].path` has its own Zarr v3 `zarr.json` with `node_type="array"`, `zarr_format=3`, and `dimension_names=["c","y","x"]`; an array is not required to repeat `ome.version`, and any OME metadata-bearing child must use the same wire version.
- Only release-qualified local directory storage, chunk grids, key encoding, data type, and standard codec combinations are emitted; all chunks and metadata are covered by the Derivative Asset manifest.
- Remote references, external chunk locations, labels, tables, high-content screening plates or wells, multiple images, time or Z axes, custom transforms, custom metadata needed for interpretation, experimental OME-NGFF versions, and mixed-version hierarchies are prohibited. Vector exchange remains DICOM Microscopy Bulk Simple Annotations rather than a private OME-Zarr convention.
- OME-Zarr and DICOM objects remain independently generated derivatives. A successful representation proves only the declared subset and transformation provenance; it does not prove generic semantic or lossless round trips.

## Validation fixtures and release gates

- The release mirrors and hashes the FHIR R4 4.0.1 core package, the complete `pathlab.fhir.shadow.r4#1.0.0` artifact set, DICOM 2026c dictionaries and tag/action policy, OME-Zarr 0.5.2 schemas and examples, terminology artifacts, and every validator dependency so qualification and production admission can run without network access.
- The reference toolchain is pinned per Release Bill of Materials. The current qualification baseline is HL7 FHIR Validator `6.10.3` with `hl7.fhir.r4.core#4.0.1`; pydicom `3.0.2`, highdicom `0.28.1`, dicomweb-client `0.61.2`, and dicom-validator `0.8.3` against edition `2026c`; and ome-zarr `0.19.1` with zarr-python `3.3.0` plus the official OME-Zarr 0.5.2 conformance artifacts. Replacing a pin requires exact ARM64, license, security, fixture, and workload requalification.
- A positive synthetic case links one Shadow Case Bundle to a calibrated WSI pyramid, all five admitted DICOM annotation geometries, the bounded OME-Zarr pyramid, and the static DZI Browser Representation through one signed cross-format identity, geometry, pixel, and provenance manifest.
- Negative fixtures cover wrong FHIR versions, package canonicals, profile versions, resources, core or semantic bindings, identifiers and unsafe free text, dangling references, invalid or PHI-bearing `OperationOutcome` resources, disallowed terminology, private or identifying DICOM content, invalid PS3.15 date actions, missing confidentiality evidence, unsupported SOP Classes, transfer syntaxes and geometries, malformed frame or annotation coordinates, absent or false Retrieve Capabilities declarations, OME-Zarr specification, wire-version or hierarchy errors, remote references, missing chunks, decompression bombs, path traversal, SSRF, duplicate identities, and concurrent replay.
- Qualification must show zero raw exchange content in logs or backups, deterministic manifests on repeated input, complete rejection and 24-hour destruction evidence, exact cross-format UID and specimen consistency, declared pixel tolerances, safe restart and resource exhaustion, and a responsive Resident Control Plane on the production ARM64 envelope.
- Each claimed path must pass the frozen fixtures and at least two independent appropriate standards implementations: FHIR clients/validators for FHIR profiles and searches, DICOMweb user agents for transactions including Retrieve Capabilities, and DICOM/OME-Zarr readers or validators for representations. This is published self-conformance evidence, not paid certification or a claim that DICOM itself certifies an implementation.
- A real EHR or PACS is never covered by the generic release result. It requires a manually approved External Registration, exact Exchange Profile and Adapter Credential, Institution-specific synthetic rehearsal, deidentified pilot, failure and revocation evidence, and an activation decision that creates no clinical, diagnostic, patient-care, universal interoperability, or paid-certification claim.
