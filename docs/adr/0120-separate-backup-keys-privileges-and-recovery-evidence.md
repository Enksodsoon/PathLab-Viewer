# Separate backup keys, privileges, and recovery evidence

The Backup Target will use LUKS2 or equivalent Institution-controlled volume encryption plus repository encryption under distinct Backup Key Versions recovered through the existing two-of-three Root Recovery Quorum. Restic and its repository key execute only on the Backup Target: production exposes a read-only object endpoint solely through signed, hash-addressed, short-lived, replay-resistant pull grants and holds no repository decryption, append, delete, prune, unlock, restore, or administration credential. Deletion-bound governed payloads are encrypted before persistence under random per-object DEKs or purpose-and-retention-epoch DEKs, and each disconnected recovery generation has a random non-derivable epoch DEK represented by three independently held shares with a two-of-three recovery threshold; automatic destruction of enough shares to make recovery impossible, plus a negative decrypt check, must be signed before age 35 days. Every protection, crypto-expiry, logical expiry, and restore result enters a hash-chained receipt signed with a dedicated Ed25519 Backup Attestation Key Version and anchored outside the online repository, and production qualification restores an actual encrypted Backup Generation through quorum recovery rather than relying on HMAC evidence or synthetic-only payloads. This refines ADR-0119's phrase "append-only production writes": it means production-originated protection work that the Backup Target pulls, verifies, and appends, never repository write authority or a repository key held by production; ADR-0119's append-only and disconnected-rotation decisions otherwise remain unchanged.
